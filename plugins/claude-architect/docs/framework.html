A coding session, run like a small engineering org.

One long-horizon orchestrator classifies the work, decomposes it into epics, specs and implementations, hands each piece to an isolated agent with a written mandate, and integrates the results through a review pipeline. It can nest — an orchestrator may hand a large spec to another — but it defaults to flat, because a manager that writes no code is the most expensive thing a run can buy. Nothing important stays implicit in conversation; it becomes an artifact an isolated agent can pick up cold.

The shape of a run

The session root talks to you; everything below it validates with its spawning agent instead. Each level owns a subtree, and the only agent type that can spawn anything at all is the orchestrator. Most runs look like the first tree — one manager, a fan of leaves.

The process

Six stages, and the order is load-bearing: each one emits an artifact the next one reads. An unrecorded decision does not exist, because the agent that needs it spawns into a fresh context and can only see what was written down.

Classify the work, then size it

Count intents. One coherent objective is a spec; several interdependent ones are an epic; a trivial change is a task. Tier follows the role the work plays, not its size — but the machinery follows footprint. Under about five files with no shared surface, the work happens in place whatever the tier says. Kind and footprint are two questions, and conflating them is what makes a 60-line change cost an epic's worth of process.

Emits the tier, the footprint estimate, and .wiki/specs/<id>.md for a spec

Assign an owner role to every sub-unit

For each spec or phase group, decide orchestrator or leaf — and write it down. Leaf is the default; a child orchestrator needs a sub-unit of three or more leaves that someone has to referee. An unrecorded choice is one that was defaulted past rather than made.

Emits one work-log line per sub-unit, e.g. spec 7e0e8fb3: leaf ×2

Branch, and isolate only what runs at once

A worktree buys exactly one thing: filesystem isolation between agents running at the same time. Top-level units and parallel siblings get one; sequential phases and fix agents commit in place. Worktrees land flat in the main repo's .worktrees/, never nested — a checkout inside a checkout duplicates disk and, on Windows, runs the combined paths into the 260-character limit. Branch names stay ---separated by tier, so the name is the record of where work sits.

Emits main--epic/<id>_name--spec/<id>_name--impl/<id>_phase, plus a worktree with its dependencies already linked

Spawn with a mandate

The spawn prompt carries only what changes per task: context and depth, the active rules slice, section-level wiki citations, the file scope, and the mandate — what this agent may decide alone and what it must escalate. The standing protocol lives in the agent definition, so it costs nothing per spawn.

Emits ACTIVE RULES · RELEVANT WIKI ENTRIES · CONTEXT · YOUR SCOPE · MANDATE — invariant fields first, so sibling spawns share a cacheable prefix

Review before every merge

Three read-only lenses, each answering a question the others don't: is the code good, does it match the spec's intent, does it still fit the project. The first two run concurrently; the third is gated on the diff having actually moved structure. Findings are grouped by locality and handed to fix agents that edit in place, then the loop re-runs until clean, until nothing above minor remains, or it escalates. Every pass is serial and therefore wall-clock the user waits through — which is why the cap is two.

Emits .review/iteration-<N>.json with a verdict of clean, needs_fixes or needs_human

Integrate, then squash up

Before a worktree is removed, the parent decides from the child's receipt whether to open its work-log at all — a clean completion with nothing the diff hides is merged unread. When it does read, it rules on each item: absorb it, lift it into its own pages, promote it to the committed wiki, or discard it because the diff already says it. Then the branch squashes into its parent and is deleted. Top-level units open a PR — the human checkpoint.

Emits one squash commit per unit, plus any durable knowledge promoted to .wiki/

Delegate or execute

The decision is keyed to the taxonomy rather than re-argued each time — and it defaults to leaves. A child orchestrator costs a fresh top-tier context that re-establishes what the parent already knew, plus its own decomposition, integration, audits and checkpoints, and then the parent pays again to read its receipt. That layer writes no code. It must earn itself by clearing both conditions: the sub-unit would itself spawn ≥3 leaves, and those leaves need file partitioning or sequencing between them.

Parallelism does not require a manager

Independent tracks that partition by file are parallel leaves — sent in one message, they run concurrently and cost nothing extra. Reach for a child orchestrator only when the refereeing between those tracks is itself the work.

Delegating is not escalating

A structural decision inside a subtree being handed to a child is delegated with that child's mandate — the parent names the boundary, the child decides within it. Escalation is only for decisions that cross the orchestrator's own boundary upward. "Too structural to hand off" means widen the child's mandate, not keep the work.

Two failure modes, and you can only see one of them

Under-delegating is visible: a root exhausts its own context integrating work it should have handed off, and returns exhausted. Over-delegating is invisible — every run succeeds, just slower and several times more expensive, because each manager re-derives what its parent already knew. Nothing in a transcript flags it. That asymmetry is why the default sits on the side you can detect: depth 2 is normal, depth 3 wants a reason, and at every level the question is what the manager does that its parent could not. If the answer is "hold two leaves", it is not a manager.

The eight agents

Each role carries two pins, both keyed to the role rather than to its depth in the tree. The model tier follows whether a mistake is silent — orchestration and architecture drift are unbounded, and a mangled merge or a missed bug slips through a gate unnoticed, so those stay top-tier. The effort level follows how much the agent must derive for itself: an orchestrator invents a decomposition from a mandate (high), while a leaf is handed CONTEXT, SCOPE, ACTIVE RULES and a work log (medium). Leaves run at medium deliberately — lower effort scopes work to what was asked, which is the same discipline the SCOPE block exists to enforce. The orchestrator is the only role that carries the sub-agent spawn tool — that grant, and nothing else, is what separates an orchestrator from a leaf.

Silent failure

An orchestrator that loses its spawn-tool grant does not error. It quietly behaves like a leaf, does everything in its own context, and the run still reports success. If nested orchestration stops happening, check the tools: line first — then check whether owner roles are being recorded at all.

Review at every boundary

MergeWhat runs
impl → spec Tests and lint. Diff review. Fix before merge.
spec → epic Full test suite. Squashed-diff review. Spec-adherence audit. Architecture-integrity audit.
epic/spec → active Architecture-integrity audit, then the review loop until clean. Then a PR, which is where you come in.

A finding is only auto-fixable if the fix is mechanical and unambiguous with no new product, architecture or security decision inside it. Anything involving a spec disagreement, a genuine tradeoff, or a security issue without an obvious mitigation sets the verdict to needs_human — and then no auto-fixes are applied at all, so the report you read is uncontaminated.

Three kinds of memory

committed · durable

.wiki/

The project's shared memory: architecture, conventions, active rules, decision records, gotchas, glossary, per-spec notes. It rides the squash-merge and outlives every branch. It is also read context, so it has a budget — a bloated wiki is a tax paid by every agent that reads it, and the default for any new entry is omit.

gitignored · ephemeral

.work-log/

AI-to-AI scratch paper, one directory per worktree. Not documentation, not for humans — bullets, file:line refs, fragments. Single-writer per file, so no locks are ever needed. It dies with its worktree, and the top-level log is deleted before the PR is pushed.

gitignored · addressed to your successor

.work-log/continue/

Resume state for one unit of work, keyed to the unit rather than the agent — because the reader is the next agent to own it. An agent cannot measure its remaining context and a parent cannot observe a running child's at all, so exhaustion is never detected: the file is refreshed at every structural boundary and is therefore always current when a compaction, crash or kill lands. State, not story; replaced, never appended.

point, don't paste

Receipts

A child's final message is copied verbatim into its parent, so writing a work-log and narrating it back pays twice. Children return ~15 lines — status, work-log path, files, and one flag for anything the diff cannot show. The saving is real only because that flag lets the parent decline to open the file at all.

request up · deliver down

Context requests

An agent missing context it should have been given does not go looking for it. It writes paused_for_context, says what it needs, and exits. The parent answers by re-spawning it with the answer attached, or passes the request further up. Nobody ever reads a grandparent's notes.

the mandate chain

Who answers to whom

Every spawn carries a written mandate: what this agent may decide, what it must escalate. Requests bubble to the nearest ancestor whose mandate covers them. The relationship is identical at every tier — leaf ⊂ child orchestrator ⊂ session root ⊂ you — so you are simply the root mandate-holder.

Override per project in .claude/settings.json. The first and third are deliberately low: review passes are strictly serial, so each one is time the user spends waiting, and concurrent leaves are bounded by disk rather than by model throughput — twenty of them running tests in twenty worktrees will thrash a machine long before the orchestrator notices.

Adopting it

/plugin marketplace add wfbcargo/PaulClaudePlugins
/plugin install claude-architect@paul-claude-plugins

Copy wiki-template/ to .wiki/ at the repo root to bootstrap the project memory, and add .claude/worktree-setup.sh if your tests need more than linked dependencies to run in a fresh checkout. Tune the model IDs in agents/*.md to whatever access you have — if you only have one capable model, point every agent at it. You keep the structure and lose only the cost optimization.

Do not put ORCHESTRATION.md in your CLAUDE.md. That file is injected into every sub-agent, so residency there multiplies an 8k-token document by the whole run's agent count — spent on leaves that never classify work or decide delegation, and whose protocol already lives in their own agents/*.md. The /architect skill reads it in the session root, which is the only context that uses it.
